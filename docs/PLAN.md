# 결정 장애 레이스 (Decision Dilemma Race) — 개발 플랜

> 지식이 아니라 **선택**으로 달리는 경주.
> 매 라운드 둘 중 하나를 고르고, **다수와 같은 선택**을 하면 전진한다.
> "남들이 뭘 고를까"를 읽는 눈치게임.

---

## 0. 결정된 전제

| 항목 | 결정 |
|---|---|
| 플레이 방식 | 온라인 실시간 멀티 + 봇 (봇은 빈자리 채우기 & 싱글 모드) |
| 우선순위 | **레이스 시각화가 1순위.** 게임 로직보다 먼저 만든다 |
| 플랫폼 | 웹 먼저 → 같은 코드로 앱(Capacitor) |
| 화면 기준 | 처음부터 **세로 9:16 + 터치 우선**. 앱 전환 때 다시 안 짜려면 필수 |

## 1. 게임 규칙

### 1.1 한 라운드 (약 20초)

```
딜레마 제시 (16초 카운트다운)
        ↓
전원 선택 (남의 선택은 안 보임)
        ↓
집계 공개 애니메이션
        ↓
이동 — 다수 전진 / 소수 제자리
        ↓
순위 갱신 → 다음 라운드
```

총 12라운드 또는 결승선(**20칸**) 선착.

### 1.2 이동 규칙 — 여기가 밸런싱의 핵심

단순히 "다수 +1, 소수 0"으로만 하면 **다수가 계속 뭉쳐서 순위가 안 갈린다.**
1등이 안 바뀌면 재미가 없다. 그래서 변동성을 넣는다.

| 상황 | 효과 |
|---|---|
| 기본 | 다수 **+2칸**, 소수 **0칸** |
| 압도 (다수 85%↑ = 7-1, 8-0) | 다수 **+1칸** — 뻔한 선택은 이득이 적다 |
| 소수 | **부스터 충전 +1** (소수가 30% 미만이면 **+2**) |
| 동점 | **전원 +1칸.** 충전도 없고 부스터도 소모되지 않는다 |

> 🔬 **"박빙 +3칸" 규칙은 폐기했다.** 1000판 시뮬레이션이 두 가지를 잡아냈다.
>
> 첫째, **8명에서 나올 수 있는 분할은 5-3(62.5%) / 6-2(75%) / 7-1(87.5%) / 8-0뿐이다.**
> "51~60%" 구간은 애초에 존재할 수 없어서 +3은 한 번도 발동하지 않는 죽은 코드였다.
> 임계값은 실제로 나올 수 있는 비율 사이에 놓아야 한다.
>
> 둘째, 임계를 65%로 고쳐서 5-3에 +3을 주자 **오히려 순응형이 유리해졌다.**
> 5-3의 5쪽은 결국 군중이고, 순응형 봇이 거기 앉아 있기 때문이다.
> 무난이 우승률 18.7% → 19.5%, 선두 교체는 3.10회 → 2.46회로 줄었다.
> 좁게 이긴 쪽에 더 주는 건 **읽은 사람이 아니라 따라간 사람에게 주는 보상**이었다.
> 그래서 일반 승리는 일괄 +2로 두고, 눈치를 보상하는 무게는 전부 부스터로 옮겼다.

### 1.2.1 부스터 — 자동 지급이 아니라 충전 게이지

**예전 설계는 밸런스를 무너뜨렸다.** 소수에 들면 부스터가 저절로 생기고,
그다음에 이긴 라운드에서 자동으로 **+6칸**이 터졌다. 24칸 트랙에서 한 방에 4분의 1이,
**내가 고르지도 않은 라운드에** 굴러 들어온다. 그건 도박이 아니라 횡재고, 그것만으로 게임이 뒤집혔다.

| | |
|---|---|
| 충전 | 소수를 고를 때마다 찬다 (극소수면 2칸) |
| 만충 | **2칸**. 그전까지 버튼은 눌리지 않는다 |
| 사용 | **버튼을 눌러야만 켜진다.** 쓸 라운드는 직접 고른다 |
| 성공 | 그 라운드 이동 **×4** |
| 실패 | 소수였으면 **충전이 그냥 날아간다** |

**틀렸을 때 잃는다는 게 타이밍을 고르는 걸 결정으로 만든다.** 자동 발동이었을 땐 고를 게 없었다.

**게이지는 버튼을 두르는 링이다.** 차오르는 것과 누르는 것이 같은 물건이어야
"이게 준비되면 내가 쓴다"가 설명 없이 읽힌다. 링이 가득 차도 저절로 터지지 않고,
버튼이 눌릴 수 있게 됐다는 뜻일 뿐이다 — 만충일 때 링이 천천히 숨 쉬는 게 그 신호다.

**켜짐과 꺼짐은 테두리 색이 아니라 채움으로 가른다.** 처음엔 둘의 차이가
테두리 틴트와 아이콘 크기뿐이었는데, **라운드 도중에 알아볼 수 있는 차이가 아니었다.**

| 상태 | 버튼 | 글씨 |
|---|---|---|
| 충전 중 | 어두운 원 + 회색 번개, **눌리지 않음** | `충전 1 / 2` |
| 만충 · 꺼짐 | 어두운 원 + **금색 링(숨 쉼)** + 금색 번개 | **`부스터 꺼짐`** |
| 켜짐 | **원 전체가 금색**, 번개는 반대로 어둡게, 밖으로 퍼지는 후광 | **`부스터 켜짐`** |

윤곽선 대 채움은 가장 오래된, 그리고 헷갈릴 수 없는 한 쌍이다.
글씨도 `준비`가 아니라 **`꺼짐` / `켜짐`**으로 못박아서 추론할 여지를 없앴다.

충전 비용과 배수도 시뮬레이션으로 정했다. **3칸/×2는 순응형이 25.5%로 오히려 악화됐다** —
2~3라운드를 버려서 +2칸 얻는 건 아무도 안 할 거래라서 소수 전략이 죽는다.
2칸/×2는 24.6%, 2칸/×3은 19.7%, **2칸/×4가 16.4%로 가장 고르다.**

> ⚠️ **동점 라운드에서 부스터가 소모되면 안 된다.** 동점은 "아무도 못 읽었다"는 뜻이라
> 누구도 부스터를 쓸 자격이 없다. 예전에 동점을 승리 처리에 묶었더니 부스터 보유자만
> 튀어나갔는데, **부스터 보유자는 정의상 직전에 소수였던 사람 = 대개 꼴찌**라서
> 맨 뒤가 갑자기 치고 나가는 것처럼 보였다. 목업에서 실제로 났던 버그다.

**부스터가 이 게임의 심장이다.** "다들 A 고를 것 같은데... 일부러 B 가서 충전할까?"
= 지금 지는 걸 감수하고 나중을 노리는 도박. 눈치게임이 두 겹이 된다.

### 1.3 특수 라운드 (지루함 방지)

| 라운드 | 이름 | 규칙 |
|---|---|---|
| 4 | **더블** | 이동 거리 2배 |
| 7 | **역전** | 소수가 전진, 다수 제자리 (라운드 시작 전 미리 공지 → 심리전 폭발) |
| 10 | **올인** | 자기 칸 수의 10~50%를 베팅. 맞히면 그만큼 얻고 틀리면 잃는다 |

> 5 / 8 / 12가 아니라 **4 / 7 / 10에 있다.** 시뮬레이션상 한 게임이 약 10라운드 만에
> 끝나기 때문에, 올인을 12라운드에 두면 **대부분의 게임에 올인 라운드가 아예 없었다.**
> 지금은 3개 중 평균 2.66개가 실제로 플레이된다.

미리 공지하는 게 포인트. "역전 라운드인 걸 다들 아니까, 다들 소수를 노리면 그게 다수가 된다."

## 2. 딜레마 카드

### 2.1 데이터 구조

```json
{
  "id": "school_012",
  "category": "학교생활",
  "a": { "text": "숙제 안 하고 지금 놀기", "emoji": "🎮" },
  "b": { "text": "숙제 먼저 하고 나중에 자유시간", "emoji": "📚" },
  "popularBias": 0.38
}
```

`popularBias` = 실제 사람들이 A를 고를 예상 비율. **봇 AI와 난이도의 기준값**이 된다.

### 2.2 카테고리

학교생활 / 인간관계 / 먹을거 / 도덕적 딜레마 / 미래·진로 / 완전 헛소리

### 2.3 목표 수량

- **142장** (한 판 12라운드 → 열 판을 해도 안 겹친다)
- 카테고리 9개: 학교생활 20 · 인간관계 20 · 먹을거 18 · 완전 헛소리 18 ·
  도덕적 딜레마 14 · 미래·진로 14 · 초능력 14 · 돈 12 · 인터넷·게임 12
- 정식: 150장

> ⚠️ **카드 퀄리티가 게임 재미의 절반이다.** 시각화가 아무리 좋아도 딜레마가 시시하면 끝.
> `popularBias`는 상상으로 채우지 말고 친구들 20명한테 실제로 물어보고 채운다.

## 3. 레이스 시각화 ⭐ 최우선

### 3.1 레이어 구조

```
┌─ UI 레이어        딜레마 카드 · 타이머 · 순위표 · 집계 바
├─ 파티클 레이어    Canvas — 먼지, 스피드라인, 부스터 불꽃, 컨페티
├─ 캐릭터 레이어    DOM — 러너 8명 (클릭/디버깅 쉬움)
├─ 트랙 레이어      SVG — 곡선 path, 칸 눈금, 결승선
└─ 배경 레이어      패럴랙스 3겹 × 테마 4종
```

**하이브리드로 가는 이유:** 캐릭터를 DOM으로 두면 CSS 애니메이션·개발자도구 디버깅이 쉽고,
파티클처럼 수백 개 도는 건 Canvas가 압도적으로 빠르다. 각자 잘하는 걸 시킨다.

### 3.2 곡선 트랙

직선 트랙은 지루하다. SVG `<path>`로 구불구불한 트랙을 그리고,
`path.getPointAtLength(진행도 × 전체길이)`로 캐릭터 좌표를 계산한다.
같은 함수로 접선 각도까지 구해서 캐릭터를 트랙 방향으로 기울인다.

### 3.3 패럴랙스 배경과 테마 (구현 완료)

3겹 (먼 0.2배속 / 중간 0.5배속 / 앞쪽 1.2배속) × 테마 4종:
**새벽 학교 → 한낮 운동장 → 도시 밤 → 우주.**

테마는 라운드가 아니라 **선두의 진행도(0~1)**에 물려 있다. 네 테마를 겹쳐 쌓고
인접한 둘의 opacity를 교차시켜서 컷이 아니라 디졸브로 넘어간다.
숫자를 안 봐도 "많이 왔구나"가 보인다 — 배경이 곧 진행바다.

> **도로 색도 테마마다 같이 바뀌어야 한다.** 배경만 밝히면 도로가 땅에 묻힌다.
> 테두리·노면·중앙선 3색을 테마별로 두고 배경과 같은 가중치로 RGB 보간한다.
> 한낮에는 밝은 회색 아스팔트에 흰 중앙선, 우주에서는 보라 노면에 네온 중앙선.
>
> 이래서 배경 테마를 Phase 3이 아니라 Phase 1에서 당겨 넣었다.
> 나중에 넣으면 레이서·도로 팔레트를 처음부터 다시 잡아야 한다.

### 3.4 레이서 — 경주용 차

위에서 내려다본 F1 스타일. 뒷바퀴가 넓고 코가 뾰족하며 리어윙과 콕핏이 있다.

**비율은 목업에서 그대로 가져온다. 눈대중으로 다시 잡으면 안 된다.**
한 번 다시 잡았다가 차 17 × 9유닛에 도로 112으로 끝났는데, 그러면

- 폰에서 차가 **20px**밖에 안 돼서 리어윙·콕핏·코 하이라이트가 전부 사라진다
- 8대 × 레인 간격 13이 도로 112을 거의 다 먹어서 **바깥 레인이 갓길을 탄다**

목업은 240유닛 월드 기준이고 이 게임은 250이므로 그대로 환산한다:

| | 목업(240 기준) | 여기(250 기준) |
|---|---|---|
| 차체 | 26 × 13 | **27 × 13.5** (약 34px) |
| 레인 간격 | 17 | **17.7** |
| 도로 | 124 (가장자리 131) | **129** (가장자리 136) |

바퀴 높이 4, 리어윙 폭 3.2, 외곽선 1.6 같은 **절대 수치도 같이 가져온다.**
차체와 함께 비례로 줄이면 바퀴가 다시 사라진다.

**레인 스태거(앞뒤 지그재그)는 뺐다.** 이웃 레인이 안 겹치게 넣은 거였는데
레인 간격만으로 충분하고, 한 대 걸러 앞뒤로 밀어 놓으니
**곡선에서 대열이 만드는 깔끔한 사선이 깨졌다.** 목업에도 없다.

차 모양이라 **스쿼시를 원보다 훨씬 세게 줄 수 있다.** 원을 늘이면 그냥 깨진 원이지만,
차를 제 길이 방향으로 늘이면 모션블러로 읽힌다. 최대 `scale(1.62, 0.72)` — 대시하는 순간
차가 확 늘어났다 착지한다. 잔상·스피드라인과 겹치면 튀어나가는 느낌이 확실히 산다.

#### 3.4.1 디테일은 공짜다 (한 번만 그리면)

차 전체가 **엔진이 통째로 옮기고 돌리고 찌그러뜨리는 정적 그룹 하나**다.
그래서 요소를 더 붙여도 프레임당 비용은 0이고, 한 번 그리는 노드 값만 든다.
붙인 것: **프론트윙 · 사이드포드 · 엔진커버 · 헬멧과 바이저 · 휠 림 하이라이트 · 후미등.**

> 헬멧은 처음에 흰 원 + 가운데 검은 원이었는데 **헬멧이 아니라 눈알로 읽혔다.**
> 회색으로 낮추고 반지름을 줄이고, 바이저를 앞쪽 절반을 가로지르는 띠로 바꿨다.

도로에도 **커브(빨강/흰색 연석)** 를 넣었다. 같은 경로를 흰색으로 굵게 한 번,
빨강으로 한 번 더 그리되 **대시 패턴을 반 주기 어긋나게** 하면 양쪽 가장자리가 한꺼번에
번갈아 칠해진다. 진짜 도형으로 그리면 곡선마다 휘어야 하는 작은 사각형이 수백 개 생긴다.

### 3.5 상시 주행 — 차가 실제로 간다

레이스 결과와 무관하게 **차는 항상 달리고 있어야 한다.** 라운드 결과는 누가 앞서느냐만 정한다.

처음엔 배경만 흘리는 **트레드밀**로 만들었는데 두 군데서 틀어졌다:

1. **출발 위치에서 이상하다.** 차가 제자리에 붙어 있고 배경만 흐르니 미끄러지는 것처럼 보인다.
2. **도로가 곡선이라 더 이상하다.** 배경을 가로로만 밀면 흐르는 방향과 도로 방향이 어긋난다.

그래서 **진짜로 전진시킨다.** 도로 위의 모든 것 — 차, 칸 눈금, 출발선, 결승선 — 을
`(점수 + cruise)` 위치에 그린다. 전부 같은 오프셋을 쓰므로 **서로 간의 거리는 정확히 점수 그대로**이고,
결승선도 20칸 앞에 그대로 있어서 1위가 20칸에 닿는 순간 실제로 만난다.
카메라가 따라가면 배경 패럴랙스는 저절로 흐른다.

| 항목 | 값 |
|---|---|
| 상시 속도 | **0.25칸/초** (16초 라운드에 4칸) |
| 트랙 길이 | 200칸 분량 + 앞쪽 12칸 |
| 앞쪽 여유(lead-in) | 출발선 뒤로도 도로가 있어야 **둥근 끝단이 안 보인다** |

### 3.5.1 엎치락뒤치락 (jostle)

전원이 같은 속도로 붙어 가면 대형이 뻣뻣하다. 각 차에 주기가 다른 파동 두 개를 겹쳐서
**±0.3칸 안쪽으로 앞뒤를 주고받게** 했다. 순위를 오독할 크기는 아니고, 살아 있어 보인다.

#### 자리만 바뀌고 속도는 그대로였던 문제

처음 버전은 위치만 흔들었다. 차는 앞뒤로 오가는데 **몸은 계속 같은 모양**이라,
치고 나가는 게 아니라 미끄러지는 것처럼 보였다. 원인은 두 가지였다.

**1. 속도를 점수에서 읽고 있었다.** 스쿼시·먼지·궤적이 전부 `점수 변화량`을 봤는데,
엎치락뒤치락은 점수를 바꾸지 않는다. 그래서 흔들리는 내내 속도가 정확히 0으로 계산됐다.
→ **실제로 그려지는 칸(`점수 + 상시주행 + 엎치락뒤치락`)의 초당 변화량**으로 바꿨다.
프레임당이 아니라 **초당**인 게 중요하다. 안 그러면 144Hz 노트북에서 모든 차가
60Hz 폰의 1/2.4 속도로 보인다.

**2. 사인파의 속도는 거의 일정하다.** 눈이 읽는 건 위치가 아니라 **미분**인데,
매끈한 사인은 밋밋하게 웅웅거린다. → 위상을 자기 자신의 사인으로 비틀었다
(`sin(θ + 0.55·sin θ)`). **앞으로 튀어나가는 건 짧고 뒤로 흘러내리는 건 길어져서**,
치고 나가는 순간이 생긴다.

| 값 | 의미 |
|---|---|
| 상대 속도 | `(그려진 칸 변화량 / dt) − 0.25` — 0이면 무리와 같은 속도, 음수면 처지는 중 |
| 몸 (`lean`) | 부호 있음. **앞서면 늘어나고 처지면 눌린다.** `|v/3|^0.6`로 굽혀서 작은 속도도 보이게 |
| 파티클 | 부호 없는 선형. 임계값을 그대로 둬서 **진짜 전진에서만** 궤적·속도선이 핀다 |
| 엔진 진동 | 세게 당길수록 **빨리 떨린다**. 위상을 누적해서 바꾸므로 주기가 변해도 안 튄다 |

측정: 3초 동안 각 차의 가로 스케일이 **0.87 ↔ 1.19** 사이를 오가고,
한 프레임 안에서 차들끼리 **0.30만큼** 벌어진다. 예전엔 전부 정확히 1.000이었다.

### 3.5.2 바람과 불꽃

| 순간 | 연출 |
|---|---|
| 다수 쪽이 전진 | 차 뒤에서 **흰 바람 줄기**가 길게 뿜어져 나옴 (0.7초) |
| ↳ 바람의 좌표계 | **화면이 아니라 트랙 좌표**에 뿌린다. 각 입자가 `(칸, 좌우 오프셋)`을 들고 뒤로 밀려나며, 매 프레임 도로 위 좌표로 투영된다. 화면 좌표에서 직선으로 날리면 **곡선 구간에서 바깥으로 튀어 나간다** |
| 부스터 발동 | 차 뒤에서 **불꽃이 화르륵** — 흰→노랑→주황→빨강, 위로 솟음 (0.95초) |

> 이펙트는 **연출 공개(reveal)가 아니라 실제 이동(moving) 시점**에 걸어야 한다.
> reveal에 걸었더니 차가 움직이기도 전에 바람이 끝나 있었다.

#### 3.5.3 "바람이 한 번 나오고 또 나온다" — 두 개의 진짜 버그

**(1) 이펙트 키를 라운드 번호로 잡았다.** 라운드 카운터는 **phase가 아직 `moving`이고
직전 결과가 화면에 그대로 있는 동안** 올라간다. 그래서 똑같은 8개의 이동이
**새 키를 달고 다시 들어와**, 이미 멈춰 선 차 뒤로 **1.7초 뒤에 두 번째 바람**이 불었다.
→ 결과가 확정될 때만 오르는 `outcomeSeq`로 키를 바꿨다. 라운드당 정확히 한 번.

측정: 캔버스에 불이 들어온 픽셀을 프레임마다 세어 봤더니
**1000ms(=REVEAL_MS)에 한 번 피고 1900ms에 사그라든 뒤, 2700ms에 두 번째 봉우리**가
또렷하게 찍혔다. 고친 뒤에는 봉우리가 하나다.

**(2) 파티클 풀이 산수상 부족했다.** 차 한 대가 프레임당 3줄, 수명 17프레임이면
7대가 동시에 뿜을 때 **바람만 360개**가 살아 있다. 거기에 먼지·잔상·속도선까지
더하면 560개 풀을 넘긴다. 넘긴 순간 `take()`가 null을 돌려주므로

- **바람이 끊겼다 자리가 나면 다시 이어진다** — 이것도 "한 번 나오고 또 나온다"로 보인다
- **불꽃은 아예 안 나온다.** 프레임당 12개 × 수명 39프레임 = 한 대가 470개를 원한다

세 가지를 함께 고쳤다:

| | 고침 |
|---|---|
| 풀 크기 | 560 → **800** |
| 분출량 | 상수 → **앞이 굵고 뒤로 가늘어지는 포락선.** 불꽃은 앞 3프레임에 11개씩 터뜨리고 꼬리만 남긴다 |
| 우선권 | 풀이 가득 차면 불꽃은 **가장 옅은 바람 줄기를 밀어내고** 자리를 잡는다 |

그리고 바람 길이를 이동 시간(`MOVE_MS`)에 맞췄다. 이동보다 오래 가는 바람은
**멈춘 차가 계속 가속하는 것처럼** 보인다.

### 3.6 카메라

- 선두와 꼴찌를 모두 담되 선두 쪽에 여유를 준다
- SVG `viewBox`를 매 프레임 lerp(0.08)로 부드럽게 보간
- 순위가 크게 바뀌는 순간 살짝 줌아웃 → 다시 줌인

#### 3.6.0 오프닝 샷 — 그리드 뒤에서 위로

레이스가 시작되면 카메라가 **그리드 바로 뒤에 붙어 낮게** 있다가
2.1초에 걸쳐 **평소의 내려다보는 프레임까지 빠져나온다.** 줌 0.75 → 1.0,
화면 안에서 차들이 오른쪽 끝에 있다가 가운데로 오고, 세로로 살짝 내려앉았다가 올라온다.

이보다 더 붙일 수는 없다. **8대가 도로를 가로로 138유닛 채우기 때문에**
더 좁히면 바깥 레인이 그냥 잘린다.

> ⚠️ 카메라 x를 0에서 잘랐더니 오프닝이 **제자리에서 멈췄다.** 0칸은 트랙 시작에서
> 46유닛밖에 안 들어와 있어서 "그리드 뒤"가 음수 x다. 하한을 `TRACK_START + 50`으로 바꿨다.

### 3.6.1 딜레마 카드 등장

A와 B가 **양쪽 화면 밖에서 쾅 날아 들어와 가운데서 부딪힌다.** 부딪히는 순간
그 자리에서 **VS가 또잉 하고 튀어나오고**, 카드는 반동으로 좌우로 밀려나 제자리에 앉고
VS는 둘 사이 가운데에 남는다. 총 0.62초.

타이밍은 셋이 공유한다 — 카드가 만나는 지점이 38%라서 VS도 거기서 시작해
카드가 아직 튕겨 나가는 동안 1.75배까지 오버슈트했다가 가라앉는다.

라운드마다 다시 재생돼야 하므로 카드 컴포넌트를 라운드 키로 remount한다.

### 3.7 결과 공개 타임라인 (게임의 하이라이트)

| 시각 | 연출 |
|---|---|
| 0.0s | 딜레마 카드 3D flip으로 뒤집힘 |
| 0.3s | 집계 바가 좌우에서 차오름 + 숫자 카운트업 |
| 0.8s | **"다수!"** 도장 쾅 (scale 1.5→1, 화면 흔들림 6px) |
| 1.0s | 다수 캐릭터 동시 대시 — 먼지 파티클 + 스피드라인 + 잔상 |
| 1.8s | 소수 캐릭터 좌절 (제자리 점프, 땀방울) |
| 2.2s | 순위표 FLIP 애니메이션으로 재정렬 |
| 2.6s | 부스터 획득자 머리 위 불꽃 아이콘 |

캐릭터 이동은 `cubic-bezier(.22,1,.36,1)` 0.8초 — 확 튀어나갔다가 부드럽게 멈춘다(ease-out).
달릴 때 squash & stretch를 넣으면 같은 코드량으로 체감 퀄리티가 두 배가 된다.

### 3.8 타이머 이펙트

16초 카운트다운은 숫자가 아니라 **이 게임의 긴장 그 자체**다. 레이스 화면 우측 상단에 원형 링 게이지로 띄운다.

| 요소 | 내용 |
|---|---|
| 색 전이 | 시안(여유) → 앰버(주의) → 코랄(촉박). RGB 보간으로 이어지고, 마지막 3초는 `pow(t,2)` 커브로 빨강이 빨리 온다 |
| **잠금 핍** | 딜레마 카드 바로 위에 인원수만큼 핍. 누군가 선택을 확정하면 왼쪽부터 하나씩 채워진다 |
| 마지막 3초 | 링이 `scale 1 → 1.11`로 심장박동, 화면 가장자리 붉은 비네트가 같은 박자로 숨 쉼. 앱에서는 햅틱 추가 |
| 내가 선택 | 링이 골드로 잠김 |
| 시간 초과 | 링이 부풀며 흩어지고 자동 랜덤 선택 |

> **잠금 핍이 핵심이다.** 몇 명이 이미 골랐는지는 보이지만 **뭘 골랐는지는 안 보인다.**
> 정보는 한 톨도 안 흘리면서 압박만 정확히 전달한다.
>
> 처음엔 링 둘레에 점으로 돌렸는데 **영락없는 타이어로 보였다.** 원형 게이지 테두리에 점을 박으면 무조건 휠이 된다.
> 링은 카운트다운만 하게 두고, 핍은 실제로 고민하는 자리인 카드 쪽에 놓는다.

## 3.6.5 게임 방법 — 읽는 게 아니라 그려진다

여섯 문단과 표 두 개였다. **첫 판을 하기 전에 아무도 안 읽는다.**
다수가 뭘 하는지 모르는 사람이 하는 눈치게임은 그냥 찍기라서, 이건 치명적이다.

그래서 규칙 하나마다 **그림이 스스로 조립되고 → 중요한 곳에 펜으로 동그라미가
그려지고 → 밑에 한 줄이 써진다.** 동그라미가 핵심 장치다. 한 곳만 가리키니까
한 장면이 한 가지 주장만 할 수 있고, 그건 산문이 강제하지 못하는 규율이다.

- 마크는 전부 `stroke-dashoffset` + `pathLength={100}`으로 그려진다.
  길이를 속성에서 정규화하니까 JS로 아무것도 재지 않고 원과 화살표가
  키프레임 하나를 공유한다.
- 원은 일부러 삐뚤다. 반지름이 흔들리고 시작점을 지나쳐 겹친다 —
  기하학적으로 완벽한 타원은 "원래 거기 있던 UI"로 읽히고,
  이건 **지금 그려지는 중**으로 읽혀야 한다.
- 글씨는 글자마다 어긋나게 올라온다. 문자열을 바꾸는 타자기가 아니라서
  스크린리더와 검색은 처음부터 문장 전체를 온전히 받는다.
- 만지기 전까지만 자동으로 넘어간다. **거스르는 자동재생은 없느니만 못하다.**
- 프레임은 300×160이 아니라 300×200이다. 폰에서 패널은 가로에 묶이므로
  **가로로 넓은 프레임은 곧 더 작은 그림**이다.

구현은 `setInterval`이 아니라 `performance.now()` 기준 `requestAnimationFrame`으로 간다.
setInterval은 탭을 옮기거나 프레임이 밀리면 시간이 조금씩 어긋나는데,
온라인에서 그 오차는 **내 화면과 남의 화면의 마감 시각이 달라진다**는 뜻이라 그냥 버그다.
reduced-motion에서는 pulse와 비네트만 끄고 링은 남긴다 — 남은 시간은 연출이 아니라 정보다.

### 3.9 성능

목표 60fps. `transform`/`opacity`만 애니메이트하고 파티클은 객체 풀로 재사용한다.
Phase 3에서 실제로 프레임을 깎아먹은 것 셋:

| 원인 | 증상 | 처리 |
|---|---|---|
| 파티클마다 `save/rotate/restore` | 대시 중 60 → 41fps | 알파를 4단계로 버킷팅해 **버킷당 `stroke()` 한 번**. 이 크기에서 4단계와 연속 페이드는 구분이 안 된다 |
| 파티클마다 `getPointAtLength` 2회 | 바람 100개 × 2 = 200회/프레임 | 트랙을 **칸당 4점으로 한 번만 샘플링**해 `Float32Array`에 넣고 선형 보간. 이 완만한 도로에서 오차는 1픽셀 미만 |
| 결과 화면 `backdrop-filter` | **25fps** | 블러 뒤에서 캔버스가 60fps로 계속 다시 그려지고 있었다. 게임이 끝나면 **레이스 루프를 아예 멈춘다** |

카운트업 숫자도 `setState`가 아니라 **ref로 DOM에 직접 쓴다** — 프레임마다 상태를 바꾸면
하필 프레임 예산이 제일 빠듯한 대시 순간에 패널 전체가 60번 다시 렌더된다.

저사양에서는 파티클 수를 자동으로 줄이고, `prefers-reduced-motion`에서는
파티클·흔들림·슬램을 전부 끄되 **남은 시간과 순위는 연출이 아니라 정보이므로 유지한다.**

## 3.9 첫 화면 — 규칙 설명

**눈치게임에서 다수가 뭘 하는지 모르면 그냥 찍기다.** 그래서 규칙 설명은 선택이 아니다.

- 첫 방문이면 `게임 방법` 화면으로 시작한다 (`localStorage`에 표시, 없으면 안 조른다)
- 제목 화면에서 언제든 다시 볼 수 있다
- 순서는 **만나는 순서대로**: 고른다 → 다수/소수 → 몇 칸 → 부스터 → 특수 라운드 → 결승
- 숫자는 전부 `rules.ts`에서 읽는다. 규칙을 튜닝하면 설명이 같이 바뀐다

## 3.10 결과 화면

- 내 등수가 **도장처럼 쾅** 찍힌다 (scale 2.2 → 0.93 → 1, -7도로 앉는다).
  라운드 도장은 지나가는 박자라 사라지지만, 이건 판정이라 남는다
- **VS는 여기까지 따라오면 안 된다.** 결과 오버레이가 반투명이라 금색 VS가
  최종 순위표를 뚫고 올라와 있었다. 게임이 끝나면 고를 게 없으니 VS도 없다

## 3.11 타이머 — 마지막 1초가 제일 시끄럽다

예전엔 3초 이하에서 `beat` 클래스가 붙고 **0.95초 고정 주기**로 뛰었다.
CSS 키프레임은 임계값에서 켜고 끄는 것밖에 못 해서, **3.0초일 때와 0.2초일 때가 똑같았다.**

지금은 rAF 루프에서 직접 그린다. 남은 시간으로 `urgency`(0~1)를 만들고 **제곱**해서
마지막 1초에 몰아준 다음, 주기·깊이·빛을 전부 거기에 태운다.

| 남은 시간 | 링 스케일 | 글로우 |
|---|---|---|
| 5초 이상 | 1.000 (안 뛴다) | 0 |
| 4초 | ~1.03 | 0 |
| 2초 | ~1.08 | 0.17 |
| 0초 | **~1.17** | **0.81** |

박동은 CSS `transform`으로 쓴다. SVG `transform` 속성으로 쓰면
`transform-origin`을 무시해서 **링이 모서리를 기준으로 커진다.**

## 3.11.5 말과 차고

트랙 위의 것들은 **차가 아니라 말**이다. 엔진은 애초에 차를 요구한 적이 없다 —
그룹 하나를 경로 위로 옮기고, 접선 방향으로 돌리고, 제 길이 방향으로 눌러줄 뿐이다.
그래서 오리도 F1 섀시만큼 잘 굴러가고, **판 위의 말이라는 쪽이 리버리보다 친근한 개념**이다.

모든 말은 `+x` 방향으로 코를 두고 원점을 중심에 두고 그려지며, 똑같은 그림자로 시작한다.
그 계약 덕분에 **새 말 하나 = `pieces.tsx`의 함수 하나**, 나머지는 손대지 않는다.

| 조건 | 얻는 말 |
|---|---|
| 처음부터 | 경주차 · 오리 · 트럭 |
| 3판 끝내기 | 버스 |
| 1등 한 번 | 고양이 |
| **꼴찌 한 번** | 거북이 |
| 부스터 터뜨리기 | 로켓 |
| 퀴즈 한 판 | 연필 |
| 퀴즈 만점 | UFO |

전부 **게임이 어차피 만들어내는 사건**이다. 세기 위해서만 존재하는 카운터를 갈게 하지 않는다.
거북이는 꼴찌용인데, 그건 어차피 너한테 일어날 일이었다.

잠긴 말도 실루엣으로 보여준다. **안 보이는 잠금은 아무것도 아니고, 보이는 잠금은 한 판 더 할 이유다.**

봇은 전부 기본 경주차다. 여덟 개가 제각각이면 동물원이 되고, 그러면 **내 말이 눈에 안 띈다 —
그게 말의 유일한 존재 이유인데.**

차고는 전부 로컬이다. **계정이 필요한 차고는 게스트가 못 여는 차고**고, 이 게임은 로그아웃 상태로 다 된다.

## 3.11.5b 볼트 — 벌고 쓰는 단위

**볼트(⚡).** 이름이 두 가지 일을 동시에 한다: 부스터 ⚡의 전압이면서, 차고 서랍의
나사 볼트다. **이 게임은 이미 그 둘 다처럼 생겼다.** 짧고, 숫자를 앞에 붙여도 안 어색하고
(300볼트), 무엇보다 **칸과 안 헷갈린다** — 트랙 점수와 같은 단위로 값을 매기는 상점은
진짜로 헷갈린다.

| 버는 곳 | 금액 |
|---|---|
| 레이스 1등 | 300 |
| 2·3등 | 150 |
| 그 외 | 60 |
| 완주(결승선 통과) | +100 |
| 퀴즈 한 문제 | 25 |
| 퀴즈 만점 | +150 |

**꼴찌도 0은 아니다.** 한 번 지고 나면 안 하게 되는 모드는 0을 주는 모드다.

### 얻는 말과 사는 말은 따로다

- **얻는 말**: 고양이(1등), 거북이(꼴찌), 로켓(부스터) — 어떻게 놀았는지에 대한 농담이다.
- **사는 말**: 버스 400, 연필 500, UFO 1200.

**"업적 아니면 돈" 으로 섞었으면 둘 다 아무것도 아니게 된다.**
살 수 있는 농담은 농담이 아니다.

### 페인트는 봇 색을 피해서 고른다

라이벌 일곱이 이미 채도 낮은 쪽을 다 갖고 있다. 청개구리와 같은 초록으로 칠하는 건
**돈을 내고 트랙에서 안 보이게 되는 것**이라, 페인트는 전부 그쪽을 피해서 뽑았다.

### 장비는 딱 하나, 그리고 혼자 하기 전용

부스터 시동(700) — 혼자 하기에서 충전 1칸을 갖고 시작한다.
**라이브에 같은 걸 붙이면 교실 상대로 유리함을 사는 게 되고, 그건 다른 종류의 게임이다.**

### 차고는 계정 페이지 안에 있다

메뉴 한 줄이었는데, 그러면 "뭘 타지"가 "뭘 하지"와 같은 선반에 놓인다.
내 것은 전부 한 곳에 — 얼굴, 이름, 말, 페인트, 볼트.
**고르는 것과 쓰는 것은 다른 결정이라서** 상점은 별도 화면이다.

## 3.11.6 퀴즈는 혼자, 기록만 잰다

퀴즈 모드에 상대는 없다. 봇도 없고 대답해주는 AI도 없다.

레이스의 축소판이 아니라 **정반대**다. 레이스는 남을 읽는 걸 채점하는데,
정답이 있는 문제엔 읽을 사람이 없다. 여기에 봇을 붙였으면 **정답을 아는 가짜 플레이어 일곱 명**이
나왔을 뿐이다.

10문제, 문제당 12초. 기록은 맞힌 개수가 먼저고 시간은 그다음이다 —
**2초 만에 아무것도 안 맞히는 건 좋은 판이 아니니까**, 시간만으로는 절대 기록을 못 깬다.

**퀴즈도 경주다.** 텅 빈 화면에 문제 하나만 떠 있었는데, 게임은 이미 트랙을 갖고 있다.
맞히면 내 말이 그만큼 나아간다. 눈금은 덱 기준이라 **덱이 몇 문제든 다 맞히면 결승선**이고,
그래서 깃발이 저쪽과 같은 뜻이 된다.

## 3.11.7 라이브 — 방장이 내고, 코드로 부르고, 실시간으로 본다

방장이 문제를 쓰고(퀴즈든 밸런스든), 코드를 불러주고, 답이 들어오는 걸 실시간으로 본다.
**인원 제한은 없다** — 스키마에도 클라이언트에도 자리(seat)라는 개념 자체가 없다.
레이스 방이 8자리를 배정하는 건 도로에 차 여덟 대가 들어가야 해서고,
라이브는 배정할 게 없어서 아무것도 배정하지 않는다.

### 트래픽이 일부러 비대칭이다

그게 "제한 없음"을 진짜로 만드는 부분이다.

| 방향 | 방식 | 비용 |
|---|---|---|
| **밖으로** (방장이 다음 문제로 넘김) | 세션 **행 하나**에 대한 realtime | 천 명이어도 행 업데이트 1번 |
| **안으로** (다 같이 답함) | 방장만 **주기적으로 집계를 물어봄** | 답 N개가 메시지 N개가 아니라 쿼리 1번 |

들어오는 답을 브로드캐스트했으면 사람이 늘수록 방장 폰이 시끄러워졌을 것이다.

### 이 스키마가 지키는 두 가지

1. **공개 전에는 아무도 정답을 못 읽는다.**
   `live_questions`에는 select 정책이 아예 없다. 방장조차 없다.
   문제는 `live_current()`로만 나가고, 그 함수는 `phase = 'revealed'`일 때만 정답과 해설을 붙인다.
2. **방장 말고는 아무도 진행하거나 실시간 집계를 못 본다.**
   방장 토큰은 `live_secrets`에 있는데, 이 테이블도 정책이 없다.
   세션 행은 누구나 읽어야 해서(그게 realtime의 통로다) 토큰을 거기 둘 수 없었다 —
   **RLS는 행 단위지 열 단위가 아니다.**

`anon` 역할로 직접 두들겨서 확인했다: 남이 시작하기·남이 집계 보기·행 직접 수정·
문제 직접 삽입·비밀 삭제·로비에서 답 제출·공개 전 집계 — **일곱 개 전부 거부**.

### 밸런스 문제의 정답은 "많은 쪽"이다

퀴즈는 정답이 있고, 밸런스는 없다. 그래서 밸런스는 **방이 고른 쪽이 곧 정답**이 된다 —
이 게임이 처음부터 하던 얘기 그대로다. 완전 반반이면 아무도 점수를 못 받는다.
레이스의 동점 처리와 같은 판단이다.

### 방장 폰이 잠겼다 돌아와도 살아남는다

코드와 토큰이 남아 있으면 세션으로 돌아온다. 이 판단은 **App에서** 한다 —
재개 로직을 라이브 화면 안에만 두면, 새로고침 후 앱은 타이틀로 열리니까
그 화면이 아예 안 뜨고 로직도 안 돈다. **스무 명이 기다리는 상황이 정확히 이걸 버텨야 하는 경우다.**

## 3.12 플레이어가 보내는 것 — 제보와 카드

| | 테이블 | 읽기 |
|---|---|---|
| 버그 제보 | `feedback` | **아무도 못 읽는다.** select 정책이 없다 — 대시보드에서만 보인다 |
| 카드 제출 | `card_submissions` | 승인된 것만 공개. 내 것은 나만 |

**낸 카드가 바로 게임에 들어가면 안 된다.** 덱이 곧 게임인데,
"숨쉬기 vs 죽기" 같은 카드 하나가 여덟 명의 라운드를 통째로 버린다.
그래서 `pending` → 손으로 확인 → `approved`가 되어야 덱에 섞인다.

승인된 카드는 앱이 시작할 때 한 번 가져와서 기본 덱에 붙인다.
**아무것도 기다리지 않는다** — 못 가져오면 원래 덱으로 그냥 시작한다.
아무도 안 쓴 딜레마보다 안 켜지는 게임이 나쁘다.

## 3.13 계정 (Phase 4.5) — 골라서 쓰는 것

이메일 매직 링크 하나만 붙였다. **대시보드 설정이 필요 없는 유일한 방법**이라서다
(OAuth 앱도, 시크릿도 없다). 익명 로그인이 첫 실행에는 더 좋지만
Auth → Providers에서 켜야 해서, 오늘 안 눌리는 버튼 대신 나중 단계로 미뤘다.

**로그인은 게이트가 아니라 업그레이드다.** 안 해도 전부 되고,
하면 이름이 기기를 따라온다 (`profiles` 테이블). 이 규칙이 깨지면
비행기 모드에서 게임이 안 켜진다.

## 4. 봇 AI

각 봇에 성향 파라미터를 준다:

| 파라미터 | 의미 |
|---|---|
| `conformity` 0~1 | 다수를 따라가려는 정도 |
| `contrarian` 0~1 | 일부러 반대로 가는 정도 |
| `risk` 0~1 | 부스터·베팅을 노리는 정도 |
| `noise` 0~1 | 그냥 랜덤하게 튀는 정도 |

선택 확률 = `sigmoid(popularBias 보정 + 성향 가중 + 노이즈)`

캐릭터 이름에 성향을 드러낸다: **무난이**(conformity 高) / **청개구리**(contrarian 高) / **눈치백단**(conformity 高 + noise 低) / **도박러**(risk 高).
플레이어가 "쟤는 어차피 반대로 갈 거야"를 읽을 수 있게 되면 게임이 한 단계 깊어진다.

## 8. 단계별 계획

### Phase 0 — 준비 (0.5일) ✅ 완료
Vite + React + TS 세팅 / 폴더 구조 / 세로 레이아웃 셸 / GitHub Pages 배포 워크플로

`.stage` 한 벌로 폰과 노트북을 다 그린다. **두 벌을 만드는 게 아니라 같은 레이아웃 한 벌**이고,
Capacitor 래핑이 재작성이 아니라 감싸기로 끝나는 이유가 이거다.

#### 레이아웃을 재사용하는 것과 모양을 강제하는 것은 다르다

처음엔 `aspect-ratio: 9/16`을 못박아서 노트북에서 **게임보다 넓은 검은 기둥 두 개**가 생겼다.
지금은 창의 높이를 다 쓰고 너비는 **9:16과 4:5 사이**에서 쓸 수 있는 만큼 쓴다.
레터박스가 넓어지는 대신 도로가 넓어진다.

> ⚠️ 프레임 모양을 풀면 **레이스 밴드가 스테이지 너비를 따라 커진다.**
> `aspect-ratio: 12/9`짜리 밴드가 노트북에서 414px까지 자라면서 순위표를 패널 밖으로 밀어냈다.
> 밴드에 절대 상한(`min(40vh, 372px)`)을 걸고, 짧은 화면(≤760px)에서는 밴드가 먼저 양보하게 했다.
> **비율(`%`) 상한은 못 쓴다** — 밴드의 부모가 auto 높이라 기준이 없어서 그냥 찌그러진다.
> 선택지 카드 최소 높이도 `132px` 고정 + 720px 분기점 하나였는데, 그 사이 높이가 전부 넘쳤다.
> `clamp(72px, 12vh, 128px)`로 바꿔서 **6가지 화면 크기 전부 넘침 0**을 확인했다.

#### 규칙은 DB에 넣지 않았다

`resolveRound()`는 이미 튜닝되고 1000판 시뮬레이션된 **유일한 규칙 정의**다.
PL/pgSQL로 한 벌 더 쓰면 **규칙서가 둘이 되고, 어긋나는 순간 두 사람이 서로 다른 위치를 본다.**

그래서 DB는 **선택만** 저장하고, 라운드가 닫히면 돌려준다.
방의 상태는 `f(고정된 덱, 고정된 명단, 닫힌 라운드들의 선택)`이고,
**위치는 아무도 안 쓴다 — 그래서 아무도 위치를 두고 다툴 수 없다.**

여기서 세 가지가 공짜로 나온다:

| | |
|---|---|
| **방장이 필요 없다** | 누구나 라운드를 닫고 넘길 수 있다. `room_next`는 멱등이라 먼저 도착한 사람이 넘기고 나머지는 no-op. **방 만든 사람이 탭을 닫아도 게임이 안 멈춘다** |
| **봇은 행도 쓰기도 필요 없다** | 선택이 `방코드:라운드`로 시드된 난수에서 나온다. 모두가 같은 걸 뽑는다 |
| **끊김은 그냥 빠진 선택** | 같은 시드로 채운다. 시간 초과와 접속 끊김이 같은 코드 한 줄이다 |

신원은 0007의 좌석 토큰을 그대로 쓴다. **여기도 같은 구멍이 있었다** —
`player_id`를 인자로 받아 믿었고 `players`는 누구나 읽는다.

`anon` 역할로 확인: 남이 시작하기·직접 choices 읽기·아직 안 끝난 라운드 열기·
안 열린 라운드에 답하기·좌석 없이 답하기 — **전부 거부.** 한 번 낸 답은 안 바뀐다(`a`를 내고
`b`를 내도 `a`가 남는다). `room_next`는 두 번 불러도 같은 값.

재생 결정성도 따로 검증했다: 세 기기가 **같은 판**을 보고(5라운드에서 끊긴 사람 포함),
방 코드가 다르면 다른 판이 나온다. 브라우저 둘로 실제 대국도 돌려서 **8라운드까지
순위표가 완전히 일치**하는 걸 확인했다 — 그동안 웹소켓은 막아놓고 폴링만으로.

#### 스키마가 지키려는 것 하나

**아무도 남의 선택을 미리 볼 수 없어야 한다.** 이걸 위해:

| 장치 | 내용 |
|---|---|
| `choices`에 SELECT 정책 없음 | RLS가 켜져 있고 정책이 없으면 **모든 읽기가 0행.** anon 키로 물어봐도 못 본다 |
| `close_round()` RPC | SECURITY DEFINER로 RLS를 넘어 읽지만, **마감 전이면 거절한다** |
| `locked_count()` RPC | **몇 명 골랐는지만** 알려준다. 뭘 골랐는지는 안 알려준다 (잠금 핍의 재료) |
| realtime 발행 제외 | `choices`는 발행 목록에 없다. 구독을 열면 숨기려던 걸 그대로 흘려보낸다 |
| 기본키 `(방, 라운드, 플레이어)` | **한 번 낸 선택은 못 바꾼다.** 핍이 차는 걸 보고 마음 바꾸기 방지 |

#### 아직 남은 구멍 — 레이스 방에만 (라이브는 닫았다)

신원이 **브라우저에 저장된 랜덤 id**라서, 방 코드를 아는 사람이
**아직 안 고른 다른 사람의 id로 선택을 대신 낼 수 있다.**

> ⚠️ 위 문장은 원래 "id를 알면"이라고 적혀 있었는데, **그건 실제보다 약하게 쓴 것이었다.**
> `players`에 SELECT 정책이 `true`라서 **id는 추측 대상이 아니라 목록으로 읽힌다.**
> 라이브에서 같은 구멍을 `anon` 역할로 재현해서 확인했다:
>
> ```
> select player_id from live_players where code = 'PROBE1'  ->  'victim-local-abc123'
> select live_answer('PROBE1', 'victim-local-abc123', 0, 'b') ->  answered 1 · B 1
> ```
>
> 답은 write-once라서, 대신 내버리면 **피해자는 아예 못 낸다.**

**라이브는 0007에서 닫았다.** 방식은 `auth.uid()` 강제가 아니라 **좌석 토큰**이다:

| | 전 | 후 |
|---|---|---|
| 신원 | 클라이언트가 보낸 id를 믿음 | 클라이언트가 만든 **비밀**로 좌석을 주장 |
| 공개 id | 그 id 그대로 (= 자격증명) | 서버가 발급한 uuid (**베껴도 쓸모없음**) |
| 좌석 테이블 | 없음 | `live_seats`, **정책 0개** — 함수 밖에선 아무도 못 읽음 |
| 로그인한 사람 | 구분 없음 | 좌석에 `user_id`가 붙고, 토큰이 새도 남이 못 씀 |

**로그인을 강제하지 않은 게 핵심이다.** 게스트가 계정 없이 계속 놀 수 있어야 하는데,
비밀은 세션마다·기기마다 하나씩이라 가입할 게 없다.

레이스 방(`players` / `choices`)에는 아직 같은 구멍이 있다. 다만 지금 로비에서
게임으로 넘어가는 경로 자체가 없어서 **실제로 낼 선택이 없다** — 그 두 줄을
살릴지 숨길지 정하고 나서 같이 처리한다.

#### 로비는 다시 살아났다

한동안 메뉴에서 빼뒀었다 — 로비에서 게임으로 가는 경로가 없어서
**아무 데도 안 가는 버튼**이었기 때문이다. 0009로 그 경로가 생겼고,
`같이 레이스`로 돌아왔다. 그때 지우지 않고 세워둔 게 그대로 쓰였다.

화면 하나가 솔로와 온라인을 **둘 다 그린다**(`GameLike`).
솔로만 가정하던 유일한 지점은 `players[0]`을 "나"로 본 것이었는데,
온라인에선 그게 대개 **남**이다.

### Phase 4.5 — 계정과 로그인 (1~2일)

온라인이 붙고 나면 "누구"가 필요해진다. 지금은 `src/net/identity.ts`가
**브라우저에만 저장되는 익명 신원**(닉네임 + 랜덤 id)을 돌려준다.
게임은 id와 표시 이름만 물어보므로, 로그인을 붙이는 건 **이 파일 하나를 바꾸는 일**이다.

| 단계 | 내용 |
|---|---|
| 지금 | `provider: "local"` — localStorage, 계정 없음. 닉네임만 |
| 로그인 도입 | Supabase Auth (카카오 / 구글 / 이메일 매직링크) → `provider: "supabase"` |
| 마이그레이션 | 로컬 신원으로 쌓인 전적을 로그인 시 계정에 귀속 — **0008에서 함** |
| 그 다음 | 전적·통계("너는 다수파 68%")·랭킹이 계정에 붙는다 |

> **중학생이 쓰는 서비스라 비밀번호를 직접 받지 않는 쪽이 낫다.**
> 소셜 로그인이나 매직링크면 비밀번호를 저장할 일도, 잃어버릴 일도 없다.
>
> 그리고 **로그인을 강제하지 않는다.** 익명으로도 끝까지 플레이할 수 있어야 하고,
> 로그인은 전적을 남기고 싶을 때 하는 선택이어야 한다.

`localStorage`는 시크릿 창이나 사이트 데이터 차단 환경에서 **읽기·쓰기 자체가 예외를 던진다.**
`identity.ts`는 전부 try/catch로 감싸서 저장이 안 되면 그냥 매번 새 익명 신원으로 돈다.

#### 차고는 계정을 따라온다 (0008)

`profiles.garage jsonb` 하나. **세이브 파일이지 테이블이 아니다** —
주인 한 명이 통째로 읽고 통째로 쓰고, 사용자 간에 조회할 일도 조인할 일도 없다.
`profiles`는 이미 `auth.uid() = id`라서 닉네임과 같은 이유로 남이 못 본다.

로컬이 여전히 **게임이 읽는 원본**이다. 로그아웃 상태로도 다 돌아가야 하니까.
이건 계정이 있을 때만 거울을 맞춰준다.

**합칠 때 아무것도 안 잃는다.** 숫자는 전부 큰 쪽, 가진 것은 합집합.

> 그래서 **가끔 후해진다** — 온라인에서 뭘 사고, 오래된 로컬 세이브로 돌아오면
> 합집합이 물건을 남기고 max가 예전 잔액을 남긴다.
>
> 그게 일부러 고른 쪽이다. **반대 방향은 애 물건을 뺏는 거고**, 여기엔 진짜 돈이 없다 —
> 상점이 파는 건 페인트, 말, 그리고 혼자 하기 전용 장비 하나뿐이다.
> **가끔 후한 쪽과 가끔 뺏는 쪽 중에서는, 이런 게임은 후한 쪽을 고른다.**

계정 페이지에 지금 어디 저장되는지 한 줄로 쓴다. **안 보이는 동기화는 아무도 안 믿는다.**
